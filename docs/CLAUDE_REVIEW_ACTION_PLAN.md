# HoneyRest 4개 프로젝트 장기 안정화 계획

상태: **리뷰 통합 완료 / 구현 보류**  
작성일: 2026-08-10  
실행 조건: 사용자가 크레딧 초기화 후 작업 시작을 명시할 때  
대상: 사용자 백엔드, 사용자 React 프론트엔드, 호스트 백엔드, 호스트 화면

## 1. 결론

현재 평가는 단기적인 화면 버그 수정 수준이 아니라 **보안 경계, 예약 재고, 결제 일관성, 테스트 격리를 다시 세우는 장기 안정화 작업**이 필요하다는 의미다.

다만 네 리뷰의 지적을 그대로 더하면 심각도가 과대 계산된다. 가격 캘린더 IDOR, 깨진 호스트 URL, 예약 상태 전달, 결제 중복 확인처럼 같은 원인이 백엔드와 프론트 리뷰에 중복 등장한다. 따라서 항목 수가 아니라 다음 공통 원인을 기준으로 작업한다.

1. 사용자·회사·관리자 권한을 요청 본문이 아니라 인증 주체에서 결정하지 않는 문제
2. 날짜별 예약 재고와 동시성 모델이 없는 문제
3. 외부 결제 성공과 내부 DB 상태를 원자적으로 복구할 장치가 없는 문제
4. 프론트가 공통 API 계층과 안전한 진입 경로를 일관되게 사용하지 않는 문제
5. 실제 로컬 DB와 초기화 코드에 의존해 안전한 회귀 테스트가 어려운 문제
6. 사용자·호스트 시스템 사이의 가격, 예약, 취소 상태 규약이 명시되지 않은 문제

현재 상태는 다음과 같이 판단한다.

| 영역 | 리뷰 기준 | 점수·판정 | 현재 판단 |
| --- | --- | --- | --- |
| 사용자 백엔드 | `main` / `e636d62` | 44/100, NO-GO | P0 재현 및 구조 개선 필요 |
| 사용자 React | `codex/react-demo-stabilization` / `9524078` | 52/100, 데모만 조건부 | 현재 기본 브랜치에서 재검증 필요 |

## 2. 작업 중지 원칙

- 이 문서는 계획만 저장한다. 아직 코드, DB, 브랜치, commit, push, PR을 변경하지 않는다.
- 사용자가 작업 시작을 명시하기 전에는 P0도 구현하지 않는다.
- 미커밋 파일은 소유자와 목적을 확인하기 전 삭제, 이동, stash하지 않는다.
- 리뷰가 본 커밋과 현재 `main`이 다르면 현재 코드에서 재현된 항목만 백로그로 확정한다.
- 프론트 리뷰 중 백엔드가 꺼진 상태에서 관찰한 500은 통합 장애 증거로 확정하지 않는다.
- 결제 테스트에는 실제 승인·취소나 실서비스 키를 사용하지 않는다.
- 이미 적용된 Flyway 마이그레이션은 수정하지 않고 새 교정 마이그레이션을 추가한다.

## 3. 원본 리뷰 통합 요약

### 3.1 사용자 백엔드

주요 P0는 예약 중복·재고 동시성 부재, Toss 승인 후 DB 실패 보상 부재, 공개된 관리자 쓰기 API, 예약 폼의 `userId` IDOR와 개인정보 노출, 비밀번호 DTO 로그, 리뷰 작성 권한 부재, 결제의 본문 `userId` 신뢰, 이메일 변경 검증 우회다.

주요 P1은 리뷰 수정 데이터 소실, 잘못된 결제 상태 판정, 찜·쿠폰·포인트 IDOR, 파일 삭제 권한 부재, 이메일 남용, 리뷰 좋아요 비멱등성, 실제 캐시 키와 다른 무효화, 로그아웃 후 토큰 생존, OAuth 토큰 주체 불일치, 잘못된 예외 HTTP 매핑, 실제 DB 의존 테스트다.

### 3.2 호스트 백엔드

주요 P0는 모든 환경에서 실행되는 고정 비밀번호 초기화, 역할 승격 가능한 회원가입, 인증 주체 타입 불일치와 `null` 회사 조회의 전체 데이터 반환, 가격 캘린더의 회사 간 읽기·쓰기 IDOR, 리뷰·문의 단건 소유권 누락이다.

주요 P1은 회사 관리자의 숙소 자가 승인, 미완성 승인 흐름, 객실을 타사 숙소로 이동할 수 있는 수정, 타 숙소 이미지 삭제, 날짜 재고 부재, 임의 예약 상태 생성, refresh token의 access token 사용, 파일 검증 부재, 깨진 예약 URL이다.

### 3.3 사용자 React

주요 P0는 `/reserve`와 결제 페이지 직접 진입·새로고침 시 `location.state` 역참조로 인한 흰 화면, Error Boundary 부재, 공통 `api` 대신 raw axios를 사용해 인증 갱신과 배포 API 주소를 우회하는 문제다.

주요 P1은 지도 키 미설정 시 대체 UI 부재, 환경 변수 문서 누락, 결제 완료 중복 확인, fetch 오류 미처리, localhost OAuth 리다이렉트, 검색 조건 불일치다. 접근성, 6.3MB 번들, 1.2MB 이미지, 코드 분할 부재는 후속 품질 트랙이다.

### 3.4 호스트 화면

주요 문제는 가격 캘린더 권한과 CSRF 정책, 누락되거나 중복된 리뷰 수정·삭제·답글 매핑, 로그인 검증 불가, 예약 목록·취소·날짜 URL 불일치다. 모바일 사이드바, 접근성 속성, 이미지 대체, 중복 CSS는 기능 안정화 뒤 처리한다.

다음 결정 없이 코드부터 고치면 사용자·호스트 저장소가 다시 어긋날 가능성이 높다.

| 신원 원천 | 모든 변경 API에서 principal의 user/company/role을 어떻게 해석할지 | 공통 권한 규칙표 |

## 5. 장기 실행 로드맵

기간은 확정 일정이 아니라 **1명 기준 약 8~12주 규모의 추정치**다. 현재 `main` 재검증 결과와 설계 결정에 따라 조정한다. 두 명이 백엔드 공통 설계를 먼저 합의하고 트랙을 나누면 4~7주로 단축할 수 있지만, 예약·결제 단계는 병렬 구현보다 규약 합의가 우선이다.

### 0단계 — 현재 코드 재검증과 안전한 작업 기반 (2~3일)

1. 세 저장소의 현재 브랜치, 원격 기본 브랜치, HEAD, 미커밋 파일을 읽기 전용으로 기록한다.
2. 네 리뷰의 각 항목에 `확인됨`, `이미 해결`, `재현 필요`, `오탐`, `중복` 상태를 붙인다.
3. 프론트 증상과 백엔드 원인이 같은 항목을 하나의 이슈로 연결한다.
4. 사용자·호스트 백엔드에 실제 로컬 DB와 분리된 test profile 전략을 세운다.
5. 호스트 초기화 코드가 테스트나 일반 실행에서 운영 데이터를 변경하지 않는지 먼저 차단 계획을 확정한다.

완료 게이트 G0:

- 모든 확정 항목에 현재 파일·메서드 근거와 재현 방법이 있다.
- 안전한 테스트 DB 또는 컨테이너 전략이 승인된다.
- 사용자 데이터와 결제를 건드리지 않고 회귀 테스트를 돌릴 수 있다.

### 1단계 — 즉시 노출 차단과 프론트 크래시 방지 (1주차)

사용자 백엔드:

- 비밀번호, 토큰, DTO, 개인정보가 로그에 남지 않도록 구조적 마스킹과 로그 레벨을 정리한다.
- banner/event/tag 관리자 쓰기 API를 역할 기반으로 제한한다.
- 예약 폼, 결제 확인, 찜 등 본문의 `userId` 대신 인증 주체를 사용한다.
- 이메일 변경은 토큰 목적·대상 이메일·중복 여부를 검증한다.

호스트 백엔드:

- 고정 SUPER_ADMIN 초기화를 `local-demo` 같은 명시적 프로필로 격리한다.
- owner/admin 가입의 역할 승격을 차단하고 SUPER_ADMIN 전용 경로를 분리한다.
- `null companyId`가 전체 조회로 이어지지 않도록 fail-closed 처리한다.
- 가격 캘린더, 결제, 리뷰, 문의의 회사 소유권 검사를 공통 서비스로 통일한다.

프론트:

- `/reserve`, 결제 처리·결과 페이지의 직접 진입과 새로고침을 안전하게 처리한다.
- 전역 Error Boundary와 사용자에게 돌아갈 경로를 제공한다.
- raw axios 호출을 전수 목록화하고 공통 `api` 전환 범위를 확정한다.

완료 게이트 G1:

- 익명 사용자가 관리자 쓰기 API를 호출할 수 없다.
- 다른 사용자·회사의 식별자를 바꿔도 데이터 읽기·변경이 실패한다.
- 민감정보가 테스트 로그에 나타나지 않는다.
- 주요 React 경로 직접 진입이 흰 화면 대신 복구 가능한 안내를 보여준다.

### 2단계 — 인증·인가·멀티테넌트 경계 완성 (2~3주차)

1. 사용자, COMPANY_ADMIN, SUPER_ADMIN별 API 권한 매트릭스를 작성한다.
2. 컨트롤러마다 흩어진 신원 해석을 하나의 principal resolver로 통합한다.
3. 쿠폰, 포인트, 찜, 리뷰, 예약, 파일, 이메일 변경의 사용자 소유권을 적용한다.
4. 숙소, 객실, 이미지, 가격, 예약, 결제, 리뷰, 문의의 회사 소유권을 적용한다.
5. 숙소 승인·거절을 SUPER_ADMIN 워크플로로 분리한다.
6. access/refresh token의 `typ`, 로그아웃·비밀번호 변경 후 폐기 정책을 적용한다.
7. 인증 방식 결정에 맞춰 CSRF, 쿠키 Secure/SameSite, CORS, 보안 헤더를 환경별로 정리한다.
   - **[완료, 2026-08-11]** 호스트 백엔드 CSRF 재활성화. `CookieCsrfTokenRepository`로 전환(STATELESS라
     기본 세션 저장소 불가), `MultipartFilter`를 `CsrfFilter`보다 앞에 빈으로 등록(이미지 업로드 폼이
     바디 파싱 전이라 `_csrf`를 못 읽던 문제), CsrfToken을 필터 체인 초입에서 강제로 미리 로드하는
     필터 추가(지연 로딩 탓에 큰 페이지에서 응답 버퍼가 먼저 커밋돼 `Set-Cookie`가 누락되던 문제).
     템플릿 34개(로그인 폼 포함)에 `_csrf` 히든 필드 추가/주석 해제. 회귀 테스트도 Spring Security 6
     기본 `XorCsrfTokenRequestAttributeHandler`(BREACH 방지 토큰 마스킹)에 맞춰 실제 페이지에서 토큰을
     읽어오는 방식으로 재작성함.
   - JWT `typ` 검증(access/refresh 구분)은 완료됨.
8. 익명·다른 사용자·다른 회사·권한 부족을 모두 포함한 negative security test를 추가한다.

완료 게이트 G2:

- 모든 변경 API는 본문·쿼리의 사용자/회사 ID를 권한 근거로 사용하지 않는다.
- 저장소 조회에 `null`을 전달해 전체 테넌트가 노출되는 경로가 없다.
- 역할별 허용·거부 테스트가 자동화되어 있다.

### 3단계 — 예약·가격·날짜별 재고 재설계 (4~5주차)

이 단계는 두 백엔드가 공유하는 하나의 설계 작업이다. 저장소별로 따로 수정하지 않는다.

1. 객실 총량이 아니라 날짜별 `available inventory`를 표현하는 스키마를 설계한다.
2. 체크인·체크아웃 구간과 예약 상태별 재고 점유 규칙을 정의한다.
3. DB 잠금, 버전 컬럼 또는 조건부 원자 갱신 중 동시성 방식을 선택한다.
4. 기본가, 날짜별 가격, 인원 추가 요금 계산을 하나의 서버 규칙으로 맞춘다.
5. 예약 생성, 결제 대기, 결제 완료, 취소, 만료 시 재고 변화를 상태도로 정의한다.
6. 예약·취소 후 검색 가용성 캐시를 정확한 키 또는 버전 방식으로 무효화한다.
7. 기존 데이터를 새 구조로 이전하는 V5 이후 교정 마이그레이션과 롤백·백업 절차를 작성한다.
8. 동일 객실 마지막 1개에 대한 병렬 예약 테스트와 경계 날짜 테스트를 추가한다.

완료 게이트 G3:

- 병렬 요청에서도 판매 수량이 재고를 초과하지 않는다.
- 사용자 화면 가격, 예약 저장 금액, Toss 요청 금액, 호스트 캘린더 가격이 일치한다.
- 취소·만료 시 재고가 정확히 한 번 복원된다.

### 4단계 — 결제 상태 머신·멱등성·보상 처리 (6~7주차)

1. 결제 시도 전 서버에 payment intent와 idempotency key를 저장한다.
2. Toss 성공을 곧바로 내부 성공으로 간주하지 않고 명시적 상태 전이를 사용한다.
3. Toss 승인 후 DB 반영 실패 시 즉시 승인 취소를 시도하고, 실패하면 재처리 대상에 기록한다.
4. 카드, 가상계좌 대기, 실패, 만료, 취소 상태를 구분한다.
5. 확인 요청의 사용자, 예약, 쿠폰, 포인트 소유권을 서버에서 재검증한다.
6. 예약 취소와 환불, 쿠폰·포인트·재고 복구를 멱등하게 처리한다.
7. 프론트 결제 성공 페이지의 새로고침·뒤로가기·중복 호출을 차단한다.
8. 외부 API timeout, 재시도, 오류 변환, 관측 가능한 감사 로그를 추가한다.
9. Toss mock으로 승인 직후 DB 오류, 중복 콜백, 네트워크 timeout을 fault injection 테스트한다.

완료 게이트 G4:

- 같은 결제 키가 여러 번 도착해도 승인·차감·예약 확정은 한 번만 발생한다.
- 외부 승인 후 내부 실패가 미확정 상태로 유실되지 않는다.
- 환불과 재고·혜택 복구의 재시도가 중복 효과를 만들지 않는다.

### 5단계 — 도메인별 P1 안정화 (8주차)

사용자 백엔드:

- 리뷰 작성은 예약 소유자이면서 COMPLETED 상태일 때만 허용한다.
- 리뷰 수정 시 createdAt·좋아요 수를 보존하고 좋아요를 사용자별 멱등 처리한다.
- 검색·추천 캐시 이름과 무효화 전략을 일치시키고 Redis `KEYS`를 제거한다.
- 파일 업로드·삭제에 소유권, MIME, 확장자, magic byte, 크기, 경로 제한을 적용한다.
- 이메일 발송 rate limit, 토큰 1회성, 계정 열거 방지를 적용한다.
- 예외를 올바른 HTTP 상태와 공개 가능한 메시지로 매핑한다.

호스트 백엔드·화면:

- 객실 수정 시 대상 숙소 소유권, 하위 이미지 소속, 예약 생성 상태를 검증한다.
- 리뷰 수정·삭제·답글과 문의 단건 경로를 실제 컨트롤러·템플릿과 일치시킨다.
- 예약 목록, 날짜, 취소 요청 URL을 하나의 라우팅 표로 통일한다.
- 로그인 실패를 NPE 없이 동일한 공개 메시지로 처리한다.

완료 게이트 G5:

- 리뷰, 파일, 이메일, 캐시, 호스트 운영 흐름의 P1 회귀 테스트가 통과한다.
- 깨진 호스트 링크와 존재하지 않는 redirect가 없다.

### 6단계 — 프론트 안정성·접근성·성능 (9주차)

사용자 React:

- 모든 HTTP 호출을 공통 API client로 통일하고 환경별 base URL을 문서화한다.
- Maps, Kakao/Google OAuth, Toss 공개 키와 map ID의 `.env.example`을 완성한다.
- 지도 키가 없거나 API가 실패할 때 대체 UI를 제공한다.
- 데이터 요청에 loading, empty, error, retry 상태를 일관되게 적용한다.
- localhost OAuth redirect와 하드코딩된 호스트 URL을 환경 변수로 전환한다.
- 모달 role, focus trap, Escape, 아이콘 이름, label 연결, 키보드 조작, 색 대비를 개선한다.
- route splitting, 대형 이미지 최적화, icon import 정리로 번들 크기를 줄인다.
- `docs/screenshots/`의 반응형이 깨진 캡처를 모든 게이트 통과 후 실제 화면으로 재촬영해 교체한다.
  그 전까지는 README에서 이 캡처들을 노출하지 않는다.

호스트 화면:

- JS가 없어도 안전한 form action과 서버 검증을 제공한다.
- 모바일 사이드바 닫기, aria-expanded, 이미지 fallback, 반응형 표·폼을 보완한다.
- 중복 테마·CSS와 네이티브 alert/confirm을 정리한다.

완료 게이트 G6:

- lint 오류 0, 경고는 허용 목록 외 0을 목표로 한다.
- 키보드만으로 핵심 예약·관리 흐름을 완료할 수 있다.
- 초기 번들 및 대형 자산의 수정 전후 수치가 기록된다.

### 7단계 — 통합 검증·운영 준비·문서 (10주차 이후)

1. 회원가입 → 인증 → 검색 → 상세 → 예약 → 결제 → 취소·리뷰의 사용자 E2E를 실행한다.
2. 호스트 로그인 → 숙소·객실 → 가격·재고 → 예약 처리 → 리뷰·문의 → 매출의 E2E를 실행한다.
3. 다른 사용자·다른 회사 접근, 동시 예약, 결제 장애를 포함한 보안·복구 E2E를 실행한다.
4. DB 백업·복원 리허설, migration dry-run, seed 프로필을 검증한다.
5. 인증 실패, 결제 보상 대기, 재고 충돌, 5xx에 대한 로그·알림·운영 대응서를 작성한다.
6. README, 환경 변수, 실행 순서, 데모 계정 생성법, 알려진 제한을 갱신한다.
7. 최신 화면 캡처는 모든 게이트 통과 후 다시 만든다.

운영 후보 게이트 G7:

- 확인된 P0가 0개다.
- 미해결 P1은 위험 수용 사유와 우회책이 문서화된 것만 허용한다.
- 자동 테스트, 수동 E2E, migration, 복구 리허설 결과가 저장된다.
- 외부 보안 재검토에서 테넌트 경계와 결제·예약 치명 이슈가 재발하지 않는다.

## 7. 작업·Git 분할 원칙

- 작업 시작 시 각 저장소의 현재 원격 기본 브랜치와 HEAD를 다시 확인한다.
- 사용자가 지정한 `main`을 기준으로 하며, 기본 브랜치 변경이나 추가 브랜치 생성은 임의로 하지 않는다.
- 한 브랜치에는 하나의 위험 주제만 둔다. 예: `auth-boundary`, `inventory-concurrency`, `payment-compensation`.
- 네 저장소를 한 커밋처럼 섞지 않는다. 공통 규약 문서를 먼저 확정하고 저장소별 구현 PR을 연결한다.
- 각 단위는 근거 테스트 → 최소 수정 → 회귀 테스트 → 문서 → 명시적 staging → commit → push → PR 순서다.
- 대용량 영상, 캡처, 로컬 설정, 서비스 계정 파일은 작업 범위에서 제외하고 삭제하지 않는다.
- merge, rebase, stash, 파일 삭제는 사용자의 명시적 요청 없이는 수행하지 않는다.

권장 PR 순서:

1. 테스트 격리와 안전한 initializer
2. 사용자 백엔드 인증·IDOR 차단
3. 호스트 백엔드 역할·테넌트 차단
4. 사용자 React 직접 진입·공통 API 안정화
5. 예약·가격·재고 공통 설계 및 백엔드별 구현
6. 결제 상태·보상 및 프론트 멱등 처리
7. 리뷰·파일·이메일·캐시 안정화
8. 호스트 라우팅·운영 화면 안정화
9. 접근성·성능·문서·E2E
