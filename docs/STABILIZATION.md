# HoneyRest 사용자 백엔드 안정화 기록

점검일: 2026-08-09

## 작업 원칙

- 인증 데이터는 사용자, 인증 토큰, 재설정 토큰이 함께 일관되게 저장되도록 한다.
- 계정 존재 여부와 내부 예외를 공개 API 응답으로 노출하지 않는다.
- 서비스 계정 JSON, 비밀번호, API 키, 로컬 미디어는 Git에 포함하지 않는다.
- 각 단계는 자동 테스트와 실행 중인 서버의 스모크 테스트를 모두 기록한다.

## 기준 상태

- 기준 브랜치 및 커밋: `main` / `8c563db`
- 사용자 API 기본 포트: 8080
- 호스트 API 기본 포트: 8081
- React 개발 서버: 5173
- 기존 작업 파일이 존재하므로 안정화 파일만 명시적으로 커밋한다.

## 사용자 인증 회귀 점검

### 원인

기존 Flyway V1의 토큰 컬럼 이름과 현재 JPA Entity의 컬럼 이름이 달랐다.

| 테이블 | 기존 컬럼 | Entity 컬럼 |
| --- | --- | --- |
| `email_verification_token` | `token`, `expires_at`, `used` | `token_value`, `expiry_date`, `is_verified` |
| `refresh_token` | `token`, `expires_at` | `token_value`, `expiry_date` |
| `password_reset_token` | `token`, `expires_at`, `used` | `token_value`, `expiry_date`, `is_used` |

회원가입은 사용자와 이메일 인증 토큰을 하나의 트랜잭션에서 저장한다. 인증 토큰 INSERT가 컬럼 불일치로 실패하면 사용자 INSERT도 롤백되므로, 화면에는 일반 500 오류가 표시되고 이후 비밀번호 찾기에서는 해당 이메일을 찾을 수 없었다.

### 수정

- V3에서 이메일 인증 토큰 스키마를 현재 Entity와 정렬했다.
- V4에서 리프레시 토큰과 비밀번호 재설정 토큰의 현재 컬럼을 추가하고 기존 데이터를 이전했다.
- 비밀번호 재설정 토큰 생성, 비밀번호 변경, 토큰 소비를 트랜잭션으로 묶었다.
- 존재하지 않는 이메일도 동일한 일반 성공 응답을 반환해 계정 존재 여부를 노출하지 않게 했다.
- 비밀번호 재설정 서비스의 성공, 미등록 이메일, 만료 토큰, 토큰 소비 테스트를 추가했다.

### 검증

```text
./gradlew test
BUILD SUCCESSFUL in 19s
```

실행 중인 로컬 서버에서도 다음을 확인했다.

| 점검 항목 | 결과 |
| --- | --- |
| `/actuator/health` | 200, `UP` |
| Flyway 마이그레이션 검증 | 4개 성공 |
| 현재 DB 스키마 버전 | 4 |
| 미등록 이메일 비밀번호 재설정 요청 | 200 일반 응답 |

실제 사용자 계정 생성이나 비밀번호 변경은 자동 점검 과정에서 수행하지 않았다.

## DB 무결성 및 데모 데이터

### 데이터와 기준 단위

- 숙소 33개: 한 행이 하나의 숙소
- 활성 객실 101개: 한 행이 하나의 객실
- 게시 리뷰 12개: 한 행이 완료 예약에 연결된 하나의 리뷰
- 사용자 이메일, 예약번호, 객실-날짜 가격은 각각 고유해야 한다.
- 숙소 `min_price`와 `rating`은 객실 및 게시 리뷰에서 파생되는 표시용 값이다.

감사 쿼리는 [scripts/audit-data-quality.sql](../scripts/audit-data-quality.sql)에 저장했다.

### 교정 전 품질 결과

| 검사 | 결과 | 심각도 | 영향 |
| --- | ---: | --- | --- |
| 숙소 최저가 불일치 | 23/33, 69.70% | 높음 | 목록 가격과 실제 예약 객실 가격이 다르게 표시됨 |
| 잘못된 지역 계층 | 1/33, 3.03% | 높음 | 홍천 숙소가 부산 지역을 참조해 지역 검색 결과가 틀림 |
| 게시 리뷰 평균 평점 불일치 | 1/33, 3.03% | 중간 | 블랙우드 표시 평점 5.0과 리뷰 평균 4.8이 다름 |
| 이미지가 없는 활성 객실 | 2/101, 1.98% | 중간 | 객실 카드에 깨진 이미지 또는 빈 공간 발생 |
| 중복 사용자 이메일 | 0 | 정상 | 사용자 식별에 영향 없음 |
| 고아 예약 | 0 | 정상 | 숙소 및 객실 참조가 유효함 |
| 범위를 벗어난 리뷰 평점 | 0 | 정상 | 평점 집계에 유효함 |
| 날짜가 없는 리뷰 | 0 | 정상 | 리뷰 시간순 정렬에 유효함 |

지역 오류는 `숲속글램핑`의 주소가 강원특별자치도 홍천군인데 `sub_region_id`가 부산광역시를 가리킨 수동 데이터 입력 오류였다. 가격과 평점 오류는 파생값을 원본 객실·리뷰 변경 후 동기화하지 않은 것이 원인이었다.

### 교정 및 재검증

- 데모 시드를 여러 번 실행해도 사용자 6명, 예약 12건, 리뷰 12건이 유지되며 중복 예약번호는 0건이다.
- 기존 호스트 가격 캘린더는 `INSERT IGNORE`로 보존한다.
- 숙소 최저가를 활성 객실의 최저 기본가와 동기화한다.
- 숙소 평점을 게시 리뷰 평균의 소수점 첫째 자리와 동기화한다.
- 홍천 데모 숙소의 하위 지역을 주소와 지역 계층이 모두 일치할 때만 교정한다.
- 데모 리뷰의 내용, 평점, 답변, 좋아요 수를 해당 `DEMO-REVIEW-30-*` 예약에만 동기화한다.

교정 후 최저가, 지역 계층, 평점 불일치는 모두 0건이다. 객실 이미지 누락 2건은 이미지 복구 단계에서 처리한다.

### Redis와 DB 일관성

리뷰 좋아요 캐시가 존재하지 않을 때 Repository가 0을 반환해 DB 값을 덮어쓰는 문제가 있었다. 캐시 미스는 `null`로 구분하도록 수정해 DB의 `like_count`를 유지한다.

블랙우드 상세 API 최종 확인값:

```text
price=69000.00
rating=4.8
reviewCount=12
reviewLikeCounts=23,31,10,14,5,21,7,16,9,27
```

## 검색 Redis 캐시 정합성

### 원인

기존 검색 캐시 키에는 날짜, 인원, 사용자 ID, 최대가격이 포함되지 않았다. 예약 가능 여부와 찜 상태가 다른 요청이 같은 캐시를 공유할 수 있었다. 또한 캐시에는 현재 페이지의 목록만 저장해 적중 시 `cachedResults.size()`를 전체 건수로 사용했고, 33개 숙소가 20개·1페이지로 축소됐다.

### 수정

- 캐시 키 버전을 `search:recommend:v2`로 분리했다.
- 위치, 좌표, 체크인, 체크아웃, 인원, 사용자, 정렬, 카테고리, 태그, 최대가격, 페이지, 크기를 모두 키에 포함했다.
- 카테고리와 태그는 정렬해 동일 조건의 파라미터 순서 차이로 중복 캐시가 생기지 않게 했다.
- 결과 목록과 전체 건수를 같은 TTL 6시간으로 별도 저장한다.
- 캐시 적중도 전체 건수가 함께 있을 때만 인정한다.

### 검증

| 요청 | 현재 페이지 건수 | 전체 건수 | 전체 페이지 |
| --- | ---: | ---: | ---: |
| 첫 번째 페이지 최초 조회 | 20 | 33 | 2 |
| 첫 번째 페이지 캐시 적중 | 20 | 33 | 2 |
| 두 번째 페이지 조회 | 13 | 33 | 2 |

캐시 키 단위 테스트는 날짜, 인원, 사용자, 최대가격의 분리와 카테고리·태그 순서 정규화를 검증한다.
